IT4IT v3

The IT Management Reference Architecture. Defines what data and functional capabilities IT needs to manage its services — across the full lifecycle from strategy to operations. Complements ITIL, COBIT, and TOGAF.

🗺️ The Big Picture

What IT4IT IS
An IT management reference architecture — defines the functional capabilities (Functional Components) and information model (Data Objects) the IT function needs to manage its services effectively.
What IT4IT is NOT
Not a process framework. IT4IT doesn't tell you how to run a Change Advisory Board — that's ITIL. IT4IT tells you what data and capabilities your tools must support.
... wait
Publisher
The Open Group — same as TOGAF and ArchiMate. Managed by the IT4IT Forum.
Relation to ITIL
ITIL = how to run IT processes. IT4IT = what data and tools those processes need. Complementary — most organisations use both.
Relation to COBIT
COBIT = what outcomes IT governance must achieve. IT4IT = the operational architecture to achieve them. Complementary.
Relation to TOGAF
TOGAF ADM produces architecture outputs (Phase A–B) that feed IT4IT's S2P value stream — strategy drives portfolio decisions.
Core idea: IT4IT treats IT like a factory — it defines the assembly line (Value Streams), the machines on the line (Functional Components), and the parts flowing through (Data Objects). The Service is what comes off the production line.

🧱 Key Structural Concepts

🔧 Functional Component (FC)
A discrete software capability the IT function needs. Each FC has defined inputs, outputs, and responsibilities. IT management tools implement FCs. ~33–40 FCs in IT4IT v3 total.
📄 Data Object
A specific, defined piece of information with content, owner, and lifecycle. Examples: Service Blueprint, Release Blueprint, Request Record, Incident Record, CMDB CI. The "nouns" of IT4IT.
🔁 Data Backbone
The shared information model and integration architecture linking all Functional Components across Value Streams. Prevents data silos. Ensures one CI record is shared by monitoring, ITSM, and CMDB tools.
🚪 Service Entry Point
The defined handoff between adjacent Value Streams — specifying exactly which Data Objects pass from one stream to the next. S2P → R2D: Service Blueprint. R2D → R2F + D2C: Service Release Blueprint.
🏷️ IT Service Model
The central shared object representing a service and its components, tracked across ALL four Value Streams. S2P funds it; R2D builds it; R2F exposes it; D2C monitors it.
📦 Digital Product (v3)
IT4IT v3 addition: IT services managed with a product-centric model — product owner, customer outcomes, backlog. Extended the S2P value stream with Digital Product Management capabilities.

1️⃣ Strategy to Portfolio (S2P)

S2P answers: "Given our business strategy, which IT services should we fund, build, maintain, and retire?" It is triggered by business demand, market change, or regulatory requirement.

S2P Functional Components
Enterprise Architecture Portfolio / Demand Management Financial Management Policy Management Service Portfolio Management
FCResponsibility
Enterprise ArchitectureAligns IT capabilities to business strategy; assesses build-vs-buy; models capability gaps
Demand ManagementCaptures and prioritises business demand before formal proposals are created
Service Portfolio ManagementGoverns all services (proposed, active, retired) — investment prioritisation and lifecycle decisions
Financial ManagementTracks total cost of ownership across service lifecycle; informs investment decisions
Policy ManagementDefines compliance and governance policies propagated as constraints to all downstream streams
S2P v3 addition: Digital Product Management introduces a product-centric operating model into S2P. A Digital Product is an IT service with a dedicated product owner, customer value proposition, and a product backlog — reflecting product-led IT delivery.

2️⃣ Requirement to Deploy (R2D)

R2D takes an approved Service Proposal from S2P and carries it through requirements, design, build, test, and controlled deployment. It is IT4IT's engineering value stream — the reference architecture for a DevOps / CI/CD toolchain.

R2D Functional Components
Requirement Management Source Control Management Build & Test Management Service Test Management Defect Management Release Management Change Management / Enablement
FCResponsibilityModern equivalent
Requirement ManagementCaptures and traces requirements from proposal to deliveryJira / Azure Boards stories
Source Control ManagementVersions code and configuration artefacts, manages branchesGit / Azure Repos
Build & Test ManagementAutomated compilation, packaging, unit and integration testingJenkins, GitHub Actions, Azure Pipelines
Defect ManagementCaptures and tracks pre-production quality defectsJira bugs, GitHub Issues
Service Test ManagementQuality gate — defines test strategy; approves release readinessTest plans, QA gates
Release ManagementPackages, schedules, and coordinates controlled deployment handoffRelease pipelines, deployment boards
Change ManagementGoverns risk assessment and authorisation of changesChange Advisory Board, automated approvals
R2D output — Service Release Blueprint: The key artefact R2D produces. Contains the complete specification of what was built, how it is configured, and what is needed to deploy and monitor it. Passed to BOTH R2F (configure catalogue) and D2C (set up monitoring).

3️⃣ Request to Fulfill (R2F)

R2F is the face of IT to its users. It takes services that R2D deployed and makes them consumable — through a catalogue, self-service portal, request handling, and automated or manual fulfilment.

R2F Functional Components
Offer Management Request Management Fulfillment Management Subscription Management Knowledge Management
FCResponsibility
Offer ManagementDefines service offerings: what is available, configuration options, SLA tiers, pricing
Request ManagementReceives, routes, and tracks user service requests — the Request Record lifecycle
Fulfillment ManagementExecutes automated or manual provisioning workflows; enforces policy during delivery
Subscription ManagementManages ongoing user entitlements — who has access to what and for how long
Knowledge ManagementStores and surfaces how-to guides, FAQs, workarounds for self-service and agent support
Service Portfolio vs Service Catalogue: Portfolio (S2P) = ALL services in all states — proposed, active, retired. Catalogue (R2F) = ONLY currently available, requestable services. The catalogue is the user-facing subset of the portfolio.

4️⃣ Detect to Correct (D2C)

D2C monitors running services, detects deviations, manages incidents and problems, controls emergency changes, and maintains configuration records. It is triggered by events, alerts, and anomalies in production.

D2C Functional Components
Event Management Incident Management Problem Management Configuration Management (CMDB) Change Control
FCResponsibilityKey artefact
Event ManagementMonitors services; filters and correlates raw signals from monitoring toolsEvent Record
Incident ManagementRestores normal service as quickly as possible — speed over root causeIncident Record
Problem ManagementInvestigates root cause; creates Known Error Records; feeds fixes into R2DProblem Record, Known Error
Configuration ManagementMaintains authoritative CMDB — CI records, attributes, and relationshipsConfiguration Item (CI)
Change ControlEmergency and remediation changes — reactive fixes to restore stabilityChange Record (emergency)
Incident vs Problem: Incident = restore service fast (even if root cause unknown). Problem = find and fix the root cause permanently. Incident Management is reactive and time-critical; Problem Management is investigative and preventive. One Problem may cause many Incidents.
D2C feedback loop: When Problem Management identifies a root cause requiring a software fix, it generates a Requirement or Change Request that enters R2D — closing the loop from production failures to engineered solutions.

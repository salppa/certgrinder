The open standard modelling language for enterprise architecture. Describes business, application, and technology architectures with precise, consistent notation — and how they relate to each other.

🗺️ The Big Picture

ArchiMate is a modelling language — not a method or process framework. It gives enterprise architects a common vocabulary and notation to describe architectures at the enterprise level, across business, application, and technology domains, with rigorous but readable diagrams.

Publisher
The Open Group — same as TOGAF and IT4IT. ArchiMate is managed by the ArchiMate Forum.
Purpose
Common language for describing, analysing, and communicating enterprise architectures to different stakeholders.
Relation to TOGAF
TOGAF provides the ADM method; ArchiMate provides the notation for creating the architecture deliverables ADM requires.
Relation to UML
UML = software design internals (class diagrams, sequence diagrams). ArchiMate = enterprise-level concerns across business, app, and tech layers.
Exam anchor: ArchiMate defines WHAT exists (elements) and HOW they are related (relationships) across the enterprise. It does not define processes for building the architecture — that is TOGAF's job.

🏗️ Framework Structure — Layers & Aspects

Every ArchiMate element sits at the intersection of a Layer (vertical domain) and an Aspect (horizontal structural role).

The Three Core Layers

Business Layer
Business actors, roles, processes, functions, services, objects. Represents the organisation and the value it delivers. Highest-level domain.
Application Layer
Application components, services, functions, data objects. Represents software systems supporting business behaviour.
Technology Layer
Nodes, system software, artifacts, paths, technology services. Infrastructure that executes and runs application software.

The Three Aspects

AspectRole in architectureExamples across layers
Active StructureStructural elements that perform behaviour — "who does it"Business Actor, Application Component, Node
BehaviourActivities, processes, functions — "what is done"Business Process, Application Function, Technology Function
Passive StructureObjects on which behaviour acts — "what it acts on"Business Object, Data Object, Artifact

🔭 Extended Framework — Beyond the Core

Aspect / LayerKey ElementsAnswers
Strategy (above Business)Capability, Resource, Course of Action, Value Stream"What can we do and how will we do it?"
Motivation (cross-cutting)Stakeholder, Driver, Assessment, Goal, Outcome, Principle, Requirement, Constraint"Why does the architecture need to be this way?"
Physical (below Technology)Equipment, Facility, Distribution Network, Material"What tangible physical assets exist?" (IoT, manufacturing)
Implementation & Migration (cross-cutting)Work Package, Deliverable, Implementation Event, Plateau, Gap"How do we get from here to there?"
Plateau & Gap: A Plateau is a stable architecture state (baseline, transition, target). A Gap is the difference between two Plateaus — what must be added, changed, or removed. Together they form the basis of an architecture roadmap.

💼 Business Layer — Key Elements

ElementWhat it modelsDistinction / Exam trap
Business ActorPhysical entity (person, team, org) that performs behaviourActor IS a physical entity; Role IS a responsibility assigned to an actor
Business RoleDefined responsibility / behaviour an actor takes onAssignment connects Actor → Role
Business ProcessSequence of activities ordered in time, triggered by an eventProcess = time-ordered; Function = competency-grouped
Business FunctionCollection of behaviour grouped by competency, regardless of time ordere.g. "Claims Processing" — not a flow, a domain
Business ServiceExternally visible value exposed to the environmentHides internal implementation; consumed by the Business or Application layer above/using it

Business CapabilityStable ability the org possesses or needsCapability-based planning; stable even when processes change

Business EventState change that triggers business behaviour"Payment Received" triggers a process — not the same as a process step

💻 Application Layer — Key Elements

ElementWhat it modelsExam tip

⚙️ Technology Layer — Key Elements

ElementWhat it modelsExam tip
NodeComputational resource — physical server, VM, container runtimeEverything that "runs" software is a Node
System SoftwarePlatform software — OS, hypervisor, DBMS, container orchestratorSpecial type of Node; runs ON infrastructure, runs other software
ArtifactPhysical deployable unit — JAR, Docker image, config filePassive element; the "package" that gets deployed to a Node
Technology ServiceExternally visible capability of a Node or System SoftwareConsumed by Application Components
Path (Communication Path)Logical or physical link between two NodesNetwork connection, VPN tunnel, API channel
Deployment pattern: Application Component → Realization → Artifact → Assignment → Node. The Component is the logical unit; the Artifact is the deployable package; the Node is where it runs.

🔗 Relationships — Complete Reference

RelationshipMeaningTypical useDirection tip
ServingOne element provides functionality to anotherApp Service serves Business Process; Tech Service serves App ComponentArrow from provider to consumer
RealizationConcrete element gives substance to an abstract oneComponent realises Service; Process realises ServiceArrow from concrete to abstract
AssignmentActive element performs behaviour / is deployed to nodeActor assigned to Role; Artifact assigned to NodeActor/Artifact → Role/Node
AccessBehaviour reads/writes a passive elementFunction accesses Data ObjectArrowhead indicates read/write/r-w
TriggeringDirect causation — one behaviour starts anotherEvent triggers Process; Process triggers another ProcessArrow from trigger to triggered
InfluenceSoft, non-causal effect on an elementDriver influences Goal; Principle influences DecisionMostly Motivation aspect
CompositionExclusive part-whole — shared lifecycleFunction is composed in Component — cannot exist independentlyFilled diamond on parent end
AggregationNon-exclusive part-whole — parts can exist independentlyComponent aggregates Nodes in a clusterOpen diamond on parent end
SpecializationIS-A / inheritance relationship"CRM Component" specialises "Application Component"Arrow from specialised to general
AssociationUnspecified or undetermined relationshipPlaceholder when exact relationship type is unclearPlain line, optional arrow
Common exam traps: Serving arrow goes from provider TO consumer (not "consuming"). Realization goes from concrete TO abstract. Composition = exclusive (filled diamond); Aggregation = shared (open diamond).
